CRO Workspace Requirements CRO Registration - Backend (Platform Administration) Feature Name CRO Administration Registration (Sign Up) User Story As a new CRO user, I want to register using my Full Name and Email Address so that I can create an account. Upon submission, I expect to receive a verification email with an activation link to verify my identity before setting my password. Explanation This feature allows CRO team members to create an account. Email verification ensures the user's identity. The password is set after verification, enhancing security by ensuring the email is valid before credentials are fully established. This supports compliance with FDA 21 CFR Part 11 regarding system access controls. Mandatory fields Full Name, Email Address Interface Messages Success: "Registration successful! Please check your email to activate your account and set your password." Error (Duplicate): "The email address is already registered. Please use a different email or sign in." Error (Invalid Email): "Please enter a valid email address." Error (Expired Token): "The activation link has expired. Please request a new registration." Business Rules Email Validation: System must validate the email format using standard regex patterns before processing. Duplicate Check: System must check for duplicate email addresses in the users table. If found, registration is rejected with the appropriate error message. Token Generation: Upon successful validation, a unique, cryptographically secure activation token must be generated and stored in the user record with an expiration timestamp (e.g., 24-48 hours). Email Template: The verification email content shall be pulled from a pre-defined template stored in the Email Templates Section of the admin panel. The template must include placeholders for the activation link. Verification Email: An email containing the activation link (www.sclinnexus.com/activate?token=[unique-token]) shall be sent to the provided address using the predefined template. Account State: The user account shall remain in an 'Inactive' or 'Pending' state in the database until the link is clicked. Post-Verification Password Setup: Upon clicking the activation link: The system shall verify the token is valid and not expired. The user shall be redirected to a Set Password page. The user must enter and confirm a password meeting complexity requirements. Upon successful password setup, the account status shall be updated to 'Active'. Password Complexity: Password must meet defined complexity rules (minimum 8 characters, at least one uppercase letter, one number, and one special character). Audit Trail (21 CFR Part 11): The system shall log the registration attempt, token generation, email delivery, token verification, and password setup events with timestamps for audit purposes. Important points: Ensure email delivery system is reliable and does not mark verification emails as spam. Activation links should expire after a defined period for security. Explanation Provides flexible and secure access. Password-based login is for standard access, while OTP offers a password less option or an additional factor for multi-factor authentication (MFA), enhancing security. (FDA 21 CFR 11.30 - Security of the system) Mandatory fields Email Address, and either Password or OTP. Interface Messages Success: Redirect to CRO Dashboard. Error (Invalid Credentials): "Invalid email address or password." Error (Inactive Account): "Your account is not yet activated. Please check your email for the activation link." Error (Invalid OTP): "The OTP entered is invalid or has expired." Info (OTP Sent): "An OTP has been sent to your registered email address." Business Rules For password login, the system must validate the email and password hash combination. For OTP login, the system must: Verify the email exists. Generate a time-based OTP and send it to the user's email. The OTP must be valid for a short duration (e.g., 5-10 minutes). Invalidate the OTP after successful use or expiry. After 5 failed login attempts, the account may be temporarily locked for a predefined period. All login attempts (success/fail) must be logged in the activity_log table. Thank you, SclinNexus Security Team Functional Considerations for Lock and Unlock a Study Category Lock / Unlock Action Description Study Lock Lock entire study Entire study is locked and becomes read-only; no further data entry or updates allowed Study Lock Attempt data entry System blocks any new data entry or modification after study is locked Study Lock Raise new query Users cannot create new queries once study is locked Study Lock Manage open queries Existing queries can only be viewed (or optionally responded based on configuration) Study Lock Subject enrollment New subject enrollment is not allowed after study lock Study Unlock Unlock entire study Study becomes active and editable again Study Unlock Resume data entry Users can enter and modify data after study is unlocked Study Unlock Query management Users can raise, respond, and close queries Study Unlock Unauthorized unlock attempt System blocks unlock if user does not have permission Study Unlock Unlock with missing reason System blocks unlock if mandatory reason is not provided Category Lock / Unlock Action Description Cross-Level Lock Study lock impact Locking study automatically locks all sites and subjects Cross-Level Lock Site lock impact Locking site automatically locks all subjects within the site Cross-Level Unlock Study unlock cascade Unlocking study may unlock all sites and subjects (based on configuration) Cross-Level Unlock Partial unlock restriction Lower-level entities cannot be unlocked if higher level is still locked Cross-Level Lock/Unlock Audit trail capture All lock/unlock actions are recorded with user, date, and reason Cross-Level Unlock Data change tracking Any data updated after unlock is fully tracked in audit logs Cross-Level Lock/Unlock System notification System sends notifications to relevant users on lock/unlock actions
